# S6 · Spatial audio after a user gesture
Verdict: PASS in the emulator for the API and the gesture rule (headless, so nobody has heard it; loudness, direction and latency on a Quest are unverified)
Date / IWSDK version / device or emulator: Tue 10 Nov 2026 / @iwsdk/core 1.1.0-rc.2 / IWSDK emulator (IWER), headless Chromium, emulated hands.

What I tried (in order):
1. Read the installed declarations: `node_modules/@iwsdk/core/dist/audio/{audio,audio-system,audio-utils}.d.ts`. `AudioSource` (component), `AudioUtils` (helpers), `PlaybackMode`, `DistanceModel` are exported from `@iwsdk/core`. `AudioSystem` is registered by the framework on every world; no feature flag is needed.
2. Generated a 0.18 s synthetic thump as a WAV (8 kB, made by a script, no external sample) and served it from `public/audio/`.
3. Temporary dev-only system `src/spikes/s6-audio.ts`: once the XR session is running, add `AudioSource { src, positional: true, refDistance: 0.5 }` to the Red tray entity, wait for `AudioUtils.preload`, call `AudioUtils.play(trayEntity)`, then log `AudioUtils.isPlaying` and the audio context state.
4. Removed the temporary import and the WAV afterwards. Nothing audible ships yet.

What worked (code snippet or path):
```ts
tray.addComponent(AudioSource, { src: `${import.meta.env.BASE_URL}audio/stamp.wav`, positional: true, refDistance: 0.5 });
AudioUtils.play(tray); // after the XR session has started
```
The framework resumes the audio context on XR session start (the "Enter XR" press is the user gesture), so no extra unlock code was needed.

Evidence (command output, screenshot path):
```

info [S6] isPlaying after 50 ms = true, context=running
info [S6] isPlaying after 600 ms = false
```
No console errors or warnings from the audio path.

Limits found by reading the installed code:
- `AudioSource` is file-based (`src` is a path loaded through `AssetManager`). There is no documented way to hand it a synthesised buffer or an oscillator.
- `AudioUtils.createOneShot` accepts `position` but ignores it in this version, and its auto-remove is a stub. Use an `AudioSource` on the entity at the right place (tray, advisor plinth) instead.
- The system pauses playing sounds when the XR session ends, and only resumes the context on session start. In the flat-browser view (no session) the context may stay suspended, so flat-browser viewers may hear nothing.
- The listener is attached to the player head, so positional sound follows head pose.

Fallback chosen (if any): none needed. Plain Web Audio stays available as the documented fallback in docs/03 if file-based sources prove limiting.

Impact on docs or tasks:
- T10 has two workable routes. (a) Render each sound in the audio brief to a small WAV with an offline script (still original, synthesised, no external samples) and play it with `AudioSource` + `AudioUtils.play`. (b) Plain Web Audio oscillators at run time, spatialised with a `PannerNode`. I recommend (a): it uses the documented IWSDK path, gets pooling and XR pause/resume for free, and the files are tiny (about 8 kB per 0.18 s at 22 kHz mono, far under the 1.5 MB budget).
- The T10 brief should give durations and synthesis recipes that can be rendered offline.
- For the remote Quest tester: is the stamp audible, does it come from the tray, and is it in time with the ring pulse?
